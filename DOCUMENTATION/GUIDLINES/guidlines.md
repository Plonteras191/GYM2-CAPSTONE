GUIDELINES FOR WRITING CHAPTER 4: RESULTS AND DISCUSSION
A Practical Guide for 4th-Year Capstone 2 Researchers

1. PURPOSE OF CHAPTER 4
Chapter 4 presents the actual results of the system development and explains what those
results mean. Researchers should use this chapter to show, in a clear and organized
manner, how the problem identified in Chapter 1 was converted into system requirements,
design, development outputs, testing results, evaluation results, and deployment results.
The sample capstone used as the basis for this guide organizes Chapter 4 according to the
same development sequence used in Chapter 3: Requirements Gathering and Analysis,
System Design, System Development, System Testing, System Evaluation, and System
Deployment.

3. THE GOLDEN RULE: DO NOT JUST SHOW—EXPLAIN
Every table, diagram, screenshot, and test result must be followed by an explanation. A
good Chapter 4 does not simply display evidence. It tells the reader what the evidence
shows, why it is important, and how it answers the study objectives.
Use this simple writing pattern for most subsections:
INTRODUCE → PRESENT → EXPLAIN → INTERPRET → CONNECT

4. 4.1 REQUIREMENTS GATHERING AND ANALYSIS PHASE
Start by explaining how information was obtained from the client or intended users. The
sample study used interviews, surveys, follow-up questions, and existing forms/documents
to identify problems, requirements, user roles, modules, and needed data.
Researchers should identify the actual evidence used in their own study, such as interviews,
questionnaires, observations, existing forms, records, or other approved data-gathering
activities. Refer readers to the appropriate appendix when necessary.
4.1-A. PROCESS DEFINITION
Describe the existing process before the proposed system was developed. Write the process
in the order that it actually happens.
Include, when applicable: (1) who performs each activity, (2) what form/document is used,
(3) what information is entered or received, (4) where information is stored, (5) what
decisions or approvals occur, (6) what the output is, and (7) what problems or delays occur.
If a manual process flow diagram is used, introduce it first and then explain the sequence
shown in the figure. Do not assume that the reader can understand the diagram without your
discussion.
Recommended paragraph order: Existing situation → step-by-step process → problems
observed → implication for the proposed system.
4.1-B. USER DEFINITION
Identify all actual users or user roles of the proposed system. For each role, state the
person's or group's responsibility and the functions they are allowed to perform.
Use a table whenever possible. Suggested columns: User Role | Main Responsibility |
System Access/Functions.
Make sure the user roles are consistent with the Use Case Diagram, Functional
Requirements, system screenshots, and testing participants. Do not list a role in one section
and omit it from the corresponding system evidence.
4.1-C. FUNCTIONAL REQUIREMENTS
Functional requirements describe what the system must do. Organize them by user role or
module.
For every functional requirement, state the action clearly. Examples of action wording
include: register an account, log in, manage user accounts, create a job posting, approve a
request, search records, submit an application, monitor application status, generate a report,
or send a notification.
Recommended table:
Table columns: No. | User/Role | Functional Requirement | Description/Purpose
After the table, explain the most important requirements and how they respond to the
problems identified during requirements gathering.

Non-functional requirements describe how the system should perform or the quality
expected from the system. The sample capstone discusses qualities such as accessibility,
availability, deployment, reliability, and security.
For each quality, provide a short, measurable or observable description appropriate to the
project. Avoid vague statements such as 'the system should be good' or 'the system should
be fast.'
Recommended table:
Table columns: No. | Quality Attribute | Requirement/Standard | How It Will Be Demonstrated
or Checked
Examples of quality areas include accessibility, availability, reliability, security,
responsiveness, usability, maintainability, and compatibility, but only include attributes that
are relevant to the project.
5. 4.2 SYSTEM DESIGN PHASE
This section shows how the requirements were translated into the structure and design of
the proposed system. The sample capstone uses system process flows, a Context Level
Diagram, Data Flow Diagram, Use Case Diagram, logical and physical ER diagrams, and a
Hi-Fi prototype/design.
For each design artifact, include the figure, a clear caption, and a written discussion. The
discussion should explain what the figure contains and how it supports the requirements.
5.1 SYSTEM PROCESS FLOW DIAGRAM
Create process flows for the important user roles or major system processes. Show the
sequence of activities from the user's starting action to the resulting output.
Before each figure, identify the role or process being presented. After the figure, explain the
important steps, decisions, inputs, and outputs.
Check that the process flow matches the actual system. If the system changed during
development, update the diagram and discussion rather than leaving an outdated process.
5.2 CONTEXT LEVEL DIAGRAM
Show the proposed system as one overall process and identify the external entities that
interact with it. Explain what information enters the system and what information is produced
or exchanged.
The written discussion should identify the major external actors and describe the relationship
between each actor and the system.
5.3 DATA FLOW DIAGRAM (DFD)
Show how data moves through the system, including inputs, processes, data stores, and
outputs. Explain the major data flows and how they support the system's functions.
Verify consistency between the DFD, functional requirements, database design, and
implemented system. Do not include processes or data stores that do not exist in the actual
project unless the figure is explicitly identified as a proposed design.
5.4 USE CASE DIAGRAM
Show the interactions between users/actors and system functions. Every major user role
should be represented where appropriate.

After the figure, explain the major use cases for each role. The use cases should agree with

5.5 LOGICAL ENTITY-RELATIONSHIP DIAGRAM
Explain the major data entities and the relationships among them at the logical level. Focus
on what information the system needs and how the entities relate to one another.
Use the ERD to demonstrate that the database structure supports the system requirements.
5.6 PHYSICAL ENTITY-RELATIONSHIP/DATABASE DIAGRAM
Present the actual database structure to be implemented or used. Discuss the important
tables/entities, fields, keys, and relationships.
The physical database diagram must agree with the actual database used by the system.
Avoid showing fields or tables that are not implemented.
5.7 HIGH-FIDELITY (HI-FI) DESIGN/PROTOTYPE
Present the visual design of the system, including major screens and interfaces. The
purpose is to show the layout, navigation, and expected user interaction.
For every major screen, explain what the screen is for, which user uses it, and which
requirement or function it supports.
Use readable screenshots. Crop unnecessary areas, keep text legible, and avoid filling the
chapter with screenshots that have no explanation.
6. 4.3 SYSTEM DEVELOPMENT PHASE
Explain how the system was actually developed. The sample capstone describes its
architecture, presentation/application/database layers, technologies, database, hosting, and
supporting development schedule.
Discuss only technologies and components actually used by the researchers. Identify the
architecture, programming languages/frameworks, database, APIs or integrations,
hosting/deployment environment, and other major components when applicable.
If a Gantt Chart is placed in an appendix, summarize its purpose and refer readers to the
appendix rather than reproducing an unnecessarily large chart in the main chapter.
Code snippets should normally be used only when they provide meaningful evidence of an
important implementation. Explain what the selected code does instead of presenting pages
of code without discussion.

7. HOW TO WRITE EACH PARAGRAPH
Use the following five-question check whenever writing a discussion paragraph:
1. What is being presented?
2. What does the table/figure/result show?
3. What are the important details?
4. What does the result mean for the project?
5. How does it connect to the objective, requirement, or next phase?
A strong paragraph answers these questions in a natural sequence. Avoid paragraphs that
merely repeat the title of a figure or say 'Figure X shows the system' without interpretation.

8. HOW TO PRESENT FIGURES
Use the following rules for every figure:
• Number figures consistently (e.g., Figure 4.1, Figure 4.2, Figure 4.3).
• Give every figure a descriptive title/caption.
• Refer to the figure in the text before or immediately around its placement.
• Explain the figure after presenting it.
• Make labels, arrows, text, and screenshots readable.
• Use the same terminology as the system and other chapters.
• Do not include decorative figures that do not provide evidence.
Suggested caption pattern: Figure 4.X. [Specific name of process/diagram/screen].
9. HOW TO PRESENT TABLES
Use tables when information is easier to compare in rows and columns, especially for
functional requirements, non-functional requirements, test cases, and evaluation results.
• Number tables consistently (e.g., Table 4.1, Table 4.2).
• Give each table a clear title.
• Define abbreviations when necessary.
• Keep column headings simple and meaningful.
• Explain the important findings after the table.
• Do not place raw data in the chapter if a summarized result is more appropriate; place
supporting raw materials in the appendix when required.
